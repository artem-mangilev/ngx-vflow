# Производительность: демо Virtualization (4900 узлов) и stress-test

Дата: 2026-09-26. Ветка `3.0`.

## Контекст

Демо Virtualization (70×70 = 4900 узлов, 4899 рёбер, ~64 700 DOM-элементов, `[optimization]="{ virtualization: true }"`, презентации `docs-node`/`docsEdge` из `@docs/shared`) было неюзабельным: загрузка страницы ~10 с, панорамирование секундными кадрами, zoom-out на 40 шагов колёсика в prod-сборке занимал 27 с.

## Метод

Playwright headless Chromium 1400×900 + CDP (`Profiler` с интервалом 250 мкс, `Performance.getMetrics`) и Long Animation Frames в странице. Сценарии: SPA-переход на страницу демо и ожидание, пока все видимые узлы измерены; pan 60 pointermove за ~1 с; drag узла 40 шагов; zoom in/out 40 wheel-событий. Инструменты и сырые прогоны: `tools/` (`profile.mjs`, `harness.js`, `heap.mjs`, `exp.mjs`, `*.jsonl`).

Встроенная браузерная панель приложения для замеров не годится: скрытая вкладка троттлит таймеры и не даёт rAF, поэтому все цифры ниже из Playwright.

```bash
npx nx serve docs --port 4201                       # dev, или .claude/launch.json → docs-4201
npx nx serve docs --configuration production --port 4300   # prod, launch.json → docs-prod
node .scratch/performance-2026-09-26/tools/profile.mjs http://localhost:4300 load,drag,pan,zoom,zoomout
node .scratch/performance-2026-09-26/tools/heap.mjs http://localhost:4201     # снапшот кучи по конструкторам
```

## Корневые причины

### 1. Квадратичная ловушка графа сигналов (главная)

`producerAccessed` в `@angular/core` (signal.mjs, Angular 20.3) перестраивает список продюсеров потребителя инкрементально, по порядку чтения. Если внутри одного реактивного вычисления сигнал читается второй раз **не подряд**, инкрементальный путь не совпадает, и Angular вызывает `isValidLink`, который линейно проходит весь список продюсеров потребителя. У потребителя с тысячами продюсеров каждое такое чтение стоит O(n), а перезапуск — O(n²).

Два места:

- Шаблон `vflow.component.html` читал `nodeTemplateDirective()` и `edgeTemplateDirective()` на каждой итерации `@for`. Встроенные view заимствуют реактивный потребитель родительского компонента, поэтому между чтениями попадают host-биндинги директив каждого элемента (`vflowKeyboardEntity().focusable()`), и каждое из 4899 чтений `edgeTemplateDirective()` проходило ~9800 ссылок. Загрузка: 4.3 с из 10.4 в dev.
- `afterRenderEffect` в `KeyboardNavigationDirective` читал `entity.vflowKeyboardEntity()` дважды на каждую из 9799 сущностей и подписывался на `focusable()` и `culled()` всех сущностей. Любая смена видимости при pan/zoom перезапускала его за 150–300 мс (dev) и до 1.7 с (prod, zoom-out).

### 2. Опрос широкого computed после каждой записи в цикле

`set nodes` вызывал `pullNode` для каждой из 4900 моделей: `renderOrder.set()` поднимает глобальную эпоху сигналов, а следующий `children()` заставляет `nodesByParentIdMap` (4901 продюсер: `nodes` + `parentId` каждого узла, потому что `createNodes` создаёт сигнал `parentId` всем) заново опросить всех продюсеров. 4900 × 4901 проверок версий ≈ 0.9 с загрузки.

### 3. Наследуемое CSS custom property, меняющееся каждый кадр

`--vflow-zoom` записывался на `.vflow-viewport` при каждом изменении вьюпорта. Свойство наследуется всеми ~65 000 элементами, и Chrome пересчитывает стиль каждого: ~18 мс на кадр zoom (recalc 336–372 мс за 20 шагов; 733 мс / 41 при zoom-out). При pan значение не менялось, поэтому pan это не затрагивало.

### 4. Презентация документации

`docs-node` рендерил текст через `[innerHTML]`: санитайзер парсит каждое значение через DOMParser — ~0.25 с на 4900 узлов. Это код docs, не библиотеки.

## Изменения

- `components/vflow/vflow.component.html` — `@let nodeTemplate` / `@let edgeTemplate` перед циклами; читаются один раз.
- `directives/keyboard-navigation.directive.ts` — `focused` стал сигналом; эффект отслеживает только список сущностей и сфокусированную сущность, пригодность остальных считается в `untracked` только при починке фокуса.
- `services/node-rendering.service.ts` + `vflow.component.ts` — `pullNodes(models)`: карта детей читается один раз до цикла записей.
- `vflow.component.ts` + `components/node/node.component.ts` — `--vflow-zoom` на вьюпорте пишется после `afterNextRender` и на `viewportChangeEnd$` (раз на жест); сфокусированный узел получает своё значение каждый кадр эффектом (только он читает `readableViewport`). Документация `design-system/overview/index.md` обновлена.
- `apps/docs/src/app/shared/flow-presentations.ts` — `[innerHTML]` только когда текст содержит разметку.
- `.claude/launch.json` — конфигурация `docs-prod` (порт 4300).

Проверено: `nx test ngx-vflow` (karma, headless) — зелёный; e2e `accessibility`, `keyboard-shortcuts`, `stress-rendering`, `viewport-gestures`, `pointer-interactions` против патченного dev-сервера — 18/18; eslint и prettier по изменённым файлам.

## Соотнесение с предложенными направлениями

- **Вынос вычислений из change detection Angular.** Уже сделано для transform/display/z-index (эффекты пишут в DOM). Главный выигрыш дала не замена биндингов, а дисциплина чтения сигналов: широкие потребители (шаблон `vflow`, эффекты уровня графа) не должны читать один сигнал дважды не подряд и не должны зависеть от каждого узла, если это не нужно. Оставшийся резерв — сокращение числа эффектов и директив на сущность (issue 02).
- **CSS.** `--vflow-zoom` был единственным per-frame свойством с наследованием на весь граф — убран с горячего пути. Дальше: меньше обёрток на узел, чтобы recalc style стоил меньше (issue 06).
- **Кэширование DOM-операций.** Чтения геометрии сами по себе дёшевы; выигрыш даст не кэш, а один проход измерения вместо трёх и данные из `ResizeObserverEntry` вместо повторных `offsetWidth` (issue 03).
- **Асимптотика.** Оказалась главной проблемой, но не в коде библиотеки, а в его взаимодействии с графом сигналов: O(n²) в `isValidLink` и O(n²) в опросе `nodesByParentIdMap`. Остались потенциальные ловушки в `sort` внутри computed (issue 04).

## Правила для сигналов в широких потребителях

1. Один сигнал — одно чтение на прогон: `@let` в шаблоне, локальная константа в эффекте/computed.
2. Не подписывать один потребитель на тысячи продюсеров без необходимости; считать пригодность лениво в `untracked`.
3. Не чередовать запись сигнала и чтение широкого computed в цикле: прочитать один раз до цикла.
4. Компаратор `sort` не должен читать сигналы: сначала снять ключи в массив, потом сортировать.
5. Никаких наследуемых CSS custom properties, меняющихся каждый кадр, на корне вьюпорта.

## Итоги тикетов 01–06

Метод: `tools/bench.mjs` против prod-сервера (`docs-prod`, порт 4300), 7 прогонов в свежих контекстах, медиана и разброс; каждая правка сравнивается с базой, собранной тем же сервером. Шум загрузки ±4–5% по медиане, кучи ±1 MB. Правка остаётся, только если эффект заметно больше шума и код не усложняется.

| Тикет                                           | Решение   | Главный эффект                                                                                 |
| ----------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------- |
| 01 ленивые observables и инжектор модели        | оставлено | куча 321 → 305 MB, pan и drag −8–9%                                                            |
| 02 меньше эффектов и директив                   | не делаем | −9 800 эффектов: загрузка в шуме                                                               |
| 03 один проход измерения                        | не делаем | выигрыш только ценой +54% к кадрам zoom-out; лишний проход в демо вызван шириной `ng-doc-pane` |
| 04 сортировка без чтения сигналов в компараторе | оставлено | пересчёт в живом потребителе 1351 → 2.5 мс на 5 000 узлов                                      |
| 05 реестр вместо content query                  | не делаем | даже без запроса загрузка в шуме                                                               |
| 06 меньше DOM-обёрток                           | не делаем | −4 900 элементов на пункт: в шуме                                                              |

Состояние prod после 01 и 04 (медиана из 7): загрузка до готовности 2.32 с, куча 305 MB, pan / drag / zoom без длинных кадров, zoom-out p90 37 мс. Весь e2e-набор (46) и unit-тесты (332) зелёные.

Оставшееся время загрузки — создание ~10 000 view Angular и первый полный style+layout ~65 000 элементов. Следующий шаг с ощутимым эффектом — не создавать view для узлов вне вьюпорта (виртуализация с монтированием по требованию), что меняет документированный контракт «DOM и состояние компонентов сохраняются».

# 03. Один проход измерения узлов и хэндлов вместо трёх

Status: wontfix
Type: task
Blocked by: —

При загрузке узлы измеряются трижды: `afterRenderEffect` в `NodeResizeControllerDirective` (первый прогон), callback `ResizeObserver` для того же элемента, затем rAF-синк хэндлов (`NodeHandlesControllerDirective.scheduleSync`) с `getBoundingClientRect` узла, хэндлов и якорей. Итого на 4900 узлов: 19 760 `getBoundingClientRect`, 14 820 `getClientRects`, 19 767 `offset*`. Микробенчмарк (`tools/exp.mjs`) показывает, что сами чтения при чистом layout стоят 1–3 мс на 4900 элементов; дорого то, что первый после DOM-записей форсирует полный style recalc + layout (~0.4 с в профиле как self-time `getClientRects`), а между проходами лежат паузы rAF/RO (~0.5 с «idle» загрузки).

Направления:

- Брать размер узла из `ResizeObserverEntry.borderBoxSize` — ни одного DOM-чтения; `afterRenderEffect`-измерение оставить только для сверки после жеста ресайза.
- Измерять хэндлы в том же проходе, что и узлы (RO-callback уже после layout), а не в отдельном rAF; общий контекст измерения (`HandleMeasureContext`) уже есть.
- `flowInitialized` не ждать два кадра, а выставлять по завершении первого прохода измерений.

Проверка: `domReads` в `profile.mjs load` должны упасть кратно, `readyMs` — на ~0.5–0.8 с в prod. Учесть спецификацию виртуализации: узел, вернувшийся из `display: none`, должен переизмериться (RO это делает сам — размер меняется с 0).

## Answer

Не делаем: проходы измерения не дублируют дорогую работу, а объединение либо не ускоряет, либо ухудшает жесты.

Замеры `tools/bench.mjs`, prod, 7 прогонов, медиана [min..max]; база после тикета 01: load.readyMs 2320 [2241..3195], куча 305.4 MB. Порог «ощутимо»: ~8% по медиане при непересекающихся диапазонах.

Профиль по фазам (`tools/phases.mjs`, dev) и покадровый лог (`tools/frames.mjs`): «дорогие» `getClientRects` (314 и 155 мс) — это принудительный style+layout, который нужен браузеру для отрисовки в любом случае; сами чтения стоят 1–3 мс на 4 900 элементов (`tools/exp.mjs`); паузы между фазами меньше 50 мс.

| Вариант                                                          | load.readyMs      | zoomout.p90 |
| ---------------------------------------------------------------- | ----------------- | ----------- |
| База                                                             | 2320 [2241..3195] | 37 мс       |
| Все синхронизации хэндлов микрозадачей вместо rAF                | 2029 [2018..2050] | 57 мс       |
| Только первая синхронизация узла микрозадачей                    | 2320 [2303..2367] | 37 мс       |
| Микрозадачей, пока flow не инициализирован                       | 2333 [2242..2341] | 37 мс       |
| Размер flow читается в `afterNextRender`, не ждёт ResizeObserver | 2256 [2206..2334] | 37 мс       |

Выигрыш первого варианта — это перенос измерения в тот же кадр; при возврате узлов в layout во время zoom-out кадры вырастают на 54%, поэтому он отклонён.

Лишний проход в демо есть, но его причина в документации: демо лежит в `ng-doc-pane`, контент которого стартует шириной 200 px (`min-width`), а ng-doc выставляет ширину через пару кадров. Узлы, попавшие во вьюпорт после расширения, измеряются ещё раз. С зафиксированной шириной панели (`STABLE=1 bench.mjs`) готовность 2197 [2172..2209] без правок библиотеки и с правкой размера flow одинаково — около −5%, ниже порога.

# Состояния блоков: React Flow, yFiles и Node-RED

Дата проверки: 2026-09-07. Материал для обсуждения production-плана flow-design-system; предложения ниже ещё не согласованы.

Проверены официальные документация и registry source React Flow UI. Приложения конкурентов в браузере не запускались; универсальный порядок наложения всех состояний не проверен.

## Где есть доказательство независимости, а где только вывод

- **Прямо документировано:** yFiles управляет selection/focus/highlight независимо; viewer поддерживает selection и focus. Поэтому режим просмотра не требует убирать доступ к ноде с клавиатуры. [Selection, Focus, and Highlight](https://docs.yworks.com/yfiles-html/dguide/view/view_selection.html)
- **Следует из отдельных API:** React Flow позволяет запретить drag/connect, сохранив focus/select. Это подход к режиму чтения, а не обещание одного универсального `readonly` флага. [Interaction props](https://reactflow.dev/api-reference/react-flow#interaction-props)
- **Проверено в исходнике:** NodeStatusIndicator выбирает одну ветку статуса через `switch`; он не читает selection, configuration validation или permissions. Отсюда можно вывести независимость данных, но нельзя обещать отсутствие визуальных конфликтов рамок. В `loading/overlay` есть перекрывающие слои; это не контракт блокировки всех операций или клавиатуры. [Registry source](https://ui.reactflow.dev/node-status-indicator)
- **Документированы отдельные каналы:** Node-RED различает configuration errors и runtime messages. Матрица всех сочетаний этих состояний в проверенной документации не приведена. [Nodes](https://nodered.org/docs/user-guide/editor/workspace/nodes)

Согласованного универсального enum «состояния ноды» у этих трёх решений не найдено. Переносить их словари целиком в headless core оснований нет.

## Предложение для ngx-vflow — ещё не решение

Разделить владельцев информации, сохранив возможность одновременного отображения:

| Ось                                                                     | Кто определяет                                       | Что требуется от представления                                                                                                                         |
| ----------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Взаимодействие: selected, focus, drag/resize                            | Core и DOM focus                                     | Доступные селекторы/контекст состояния; focus остаётся заметен поверх прикладных статусов. Не каждый флаг обязан получать отдельный визуальный эффект. |
| Возможности: можно перемещать, соединять, выбирать, фокусировать        | Приложение настраивает поддерживаемое поведение core | У недоступного действия нет ложного affordance; запрет соединения не делает всю ноду недоступной для инспекции.                                        |
| Текущая попытка соединения: допустимо / недопустимо / ещё нет кандидата | Core вызывает правило приложения                     | Индикация конкретного порта и connection preview; не менять этим статус всей ноды.                                                                     |
| Ошибки/предупреждения модели                                            | Приложение                                           | Место для индикатора и пояснения; выбранная нода всё ещё показывает диагностику. UI не реализует валидатор графа.                                      |
| Прикладной статус: исполнение, подключение, синхронизация и др.         | Приложение                                           | Составная часть для подписи/иконки/семантического тона и, при необходимости, активности. Не навязывать ERD или BPMN жизненный цикл workflow.           |

Минимальная форма UI-контракта для обсуждения: индикатор с произвольной подписью/иконкой и небольшим набором семантических тонов, плюс независимый признак активности, если он нужен. `running`, `queued`, `cancelled`, `connected` остаются словами приложения. Альтернатива — готовый ограниченный enum как у React Flow UI; он проще в использовании, но уже по охвату.

Это не предложение создавать общую state machine, менеджеры состояний или отдельную директиву на каждый флаг. Существующие сигналы, контекст и DOM-состояния нужно сначала переиспользовать. Конкретный API требует сверки с текущим core.

Семантический параметр вроде «есть предупреждение» передаёт смысл и не равен удаляемому параметру оформления вроде `resizerColor`. Внешний вид такого состояния остаётся на CSS-токенах.

## Правила сочетания для обсуждения

1. Не делать единый приоритет `error > selected > running`: потеряется информация. Проверить selected + focus + error и selected + running отдельными демонстрационными случаями.
2. Сохранить отдельные каналы для selection/focus и прикладной диагностики/статуса; точный вид каналов выбрать в следующих визуальных задачах.
3. Busy само по себе не блокирует взаимодействие. Приложение отдельно управляет допустимыми действиями.
4. Read-only запрещает изменение модели, но может разрешать выделение, навигацию, копирование и просмотр сведений. `disabled` кнопки и «выключена из workflow» — разные понятия.
5. Ошибка конфигурации и ошибка исполнения — разные причины. Приложение решает актуальность диагностик и результатов; UI не выводит это из цвета или одного общего `error`.
6. Семантические токены должны позволять различать selection/focus, допустимость подключения и прикладной тон. Одного `--error-color` недостаточно для определения поведения или приоритета.

## Осталось выбрать с пользователем

- Достаточен ли общий индикатор (тон + содержимое + необязательная активность), или в общей UI-основе нужен enum жизненного цикла исполнения?
- Должны ли диагностика и прикладной статус иметь отдельные составные части/места, чтобы одновременно показывать warning и running?
- Какие сочетания обязательны в production-демо: selected+focus+error; selected+running; read-only+focus; запрещённое соединение при валидной ноде?
- Нужно ли самостоятельное состояние highlight для результатов поиска/связанного пути уже сейчас? yFiles показывает пользу, но само наличие у конкурента не определяет наш scope.

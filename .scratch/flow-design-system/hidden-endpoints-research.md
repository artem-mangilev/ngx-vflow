# Связи со скрытыми полями: React Flow, JointJS и GoJS

Дата проверки: 2026-09-07. Вопрос Q8a для production-плана flow-design-system.

Область: внутренний scroll списка полей и collapse содержимого одной ноды с портами строк. Сворачивание целого подграфа — другой сценарий, его примеры не доказывают поведение портов внутри ноды. Это исследование документации и исходников, без браузерного прогона конкурентов. Ниже отдельно обозначены проверенные контракты и наши предложения.

## Сравнение

| Библиотека / слой                       | Проверенное поведение                                                                                                                                                                                                           | Что нельзя считать готовой гарантией                                                       |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| React Flow, общие handles               | Порты имеют ID; при изменении положения приложение вызывает `useUpdateNodeInternals`. [Handles](https://reactflow.dev/learn/customization/handles), [hook](https://reactflow.dev/api-reference/hooks/use-update-node-internals) | Автоматическое превращение скрытого поля в порт заголовка / границы не описано в этих API. |
| React Flow UI, Database Schema Node     | Композиция оболочки, header, таблицы, строк и ячеек. [Компонент](https://reactflow.dev/ui/components/database-schema-node)                                                                                                      | В проверенном компоненте нет политики scroll/collapse endpoints.                           |
| JointJS+, Record                        | Есть отдельные SVG-цели для связей с полями выше и ниже видимой области. [Record](https://docs.jointjs.com/api/shapes/standard/Record/)                                                                                         | Поведение nested collapse нельзя выводить из контракта scrolling.                          |
| GoJS, ScrollingTable sample + extension | Невидимые строки сохраняются в visual tree, получают нулевой размер и позицию на соответствующей границе таблицы. [Sample](https://gojs.net/latest/samples/ScrollingTable)                                                      | Это готовый пример с расширением, а не универсальная настройка любой ноды.                 |

## React Flow

Для нескольких портов одного типа нужны уникальные `id`; связь ссылается на них через `sourceHandle` / `targetHandle`. Скрывать handle документация рекомендует через `visibility: hidden` или `opacity: 0`: `display: none` уничтожает измеримые размеры. Это способ сохранить геометрию невидимого порта, а не способ перенести его к границе списка. [Handles](https://reactflow.dev/learn/customization/handles)

Позиции DOM handles измеряются через `getBoundingClientRect()` относительно ноды с учётом zoom и сохраняются во внутренних данных. Проверенный измеритель не ограничивает координаты границей scroll-контейнера. Следовательно, простое обновление измерений и выбор видимой точки для скрытого поля — две разные задачи. [Исходник getHandleBounds](https://github.com/xyflow/xyflow/blob/main/packages/system/src/utils/dom.ts)

Официальный контракт требует `useUpdateNodeInternals` после программного изменения количества или положения handles. Практический вывод для внутреннего DOM-scroll: приложение должно обеспечить обновление измерений после изменения положения и отдельно решить, где показывать невидимые endpoints; hook сам такую политику не обещает. [Документация hook](https://reactflow.dev/api-reference/hooks/use-update-node-internals), [исходник hook](https://github.com/xyflow/xyflow/blob/main/packages/react/src/hooks/useUpdateNodeInternals.ts)

Если при расчёте ребра handle с указанным ID отсутствует, `getEdgePosition` сообщает ошибку `008` и возвращает `null`. Автоматического поиска «родительского» порта для указанного, но исчезнувшего ID в этом пути нет. Это не означает удаления записи связи из пользовательских данных. [Исходник getEdgePosition](https://github.com/xyflow/xyflow/blob/main/packages/system/src/utils/edges/positions.ts)

Проверен также код, который отдаёт официальный registry: `DatabaseSchemaNodeBody` содержит обычную таблицу с `overflow-visible`, строки — обёртки `TableRow`. В файле нет scroll-listener, collapse, proxy endpoint или агрегации связей. В официальном usage ID берётся из `entry.title`; для нашего требования rename без разрыва связей это нельзя копировать буквально — нужен ID, независимый от отображаемого названия. [Registry JSON с исходником](https://ui.reactflow.dev/database-schema-node), [usage](https://reactflow.dev/ui/components/database-schema-node)

Вывод ограничен проверенными публичными компонентами и путями core: нельзя заявлять, что React Flow «из коробки прячет связи» или «из коробки переносит их на header» при внутреннем collapse.

## JointJS+

`Record` явно различает два случая. `isItemVisible` отвечает за скрытие collapsed-предком; `getItemViewSign` различает видимое поле, поле выше и ниже viewport. Последний метод бросает ошибку для поля внутри collapsed-предка. Scrolling включается через числовой `scrollTop`; без него Record увеличивает размер под содержимое. [Record API](https://docs.jointjs.com/api/shapes/standard/Record/)

`itemAboveViewSelector` и `itemBelowViewSelector` определяют SVG-элемент, к которому связь **визуально** переподключается, когда исходное поле ушло вверх или вниз. Это документированный механизм отображения proxy endpoint, не обещание объединить несколько рёбер в одно. По смыслу контракта меняется визуальная привязка; отдельной проверки сериализованной модели до/после scroll здесь не было. [Record API](https://docs.jointjs.com/api/shapes/standard/Record/)

`RecordScrollbar` — отдельный инструмент для Record; он исчезает, если все поля помещаются. Record относится к JointJS+, а не к открытой базовой библиотеке. [RecordScrollbar](https://docs.jointjs.com/api/elementTools/RecordScrollbar/), [официальное описание Record shapes](https://docs.jointjs.com/learn/features/ready-to-use-shapes/records/)

Ограничение доказательств: платный исходник RecordView не проверялся; встроенный CodeSandbox из документации не удалось загрузить. Поэтому точную цель связи при nested collapse, восстановление ID и взаимодействие с proxy подтверждёнными не считаем. Существование `toggleItemCollapse` само по себе этого не доказывает.

## GoJS

Официальный ScrollingTable sample прямо описывает геометрию: элементы до `Panel.topIndex` располагаются вверху таблицы с нулевым размером; элементы после видимой части — внизу. Связи продолжают относиться к исходным портам. Вывод из этого устройства: несколько концов могут совпасть на границе, но это не слияние моделей рёбер и не замена ID на общий порт. [Sample с объяснением поведения](https://gojs.net/latest/samples/ScrollingTable)

В исходнике расширения `incrTableIndex` меняет `table.topIndex`, вызывает `node.invalidateConnectedLinks()` и обновляет scrollbar. Следовательно, изменение scroll сопровождается явной инвалидизацией связанной геометрии. Расширение не входит в основной API GoJS; авторы рекомендуют копировать его в проект для production, поскольку API расширения может изменяться даже в patch-релизах. [ScrollingTable.ts](https://github.com/NorthwoodsSoftware/GoJS/blob/master/extensionsJSM/ScrollingTable.ts)

Это scene-graph layout GoJS, поэтому рецепт нулевого размера нельзя механически перенести на DOM handles React Flow / ngx-vflow. В этом sample не проверен отдельный сценарий collapse полей. Перенос endpoints при scroll доказан текстовым описанием и исходником, не скриншотом.

## Предложение для ngx-vflow — пока не принятое решение

Исследование поддерживает разделение **логического endpoint** и **его текущей видимой позиции**. Для первого production-демо разумен следующий вариант:

1. Поле всегда имеет стабильный ID, независимый от названия, порядка строк и scroll. Scroll/collapse не меняют `sourceHandle` / `targetHandle` в данных связи.
2. При scroll endpoint остаётся у своей строки, пока она видна; иначе показывается у верхней/нижней границы списка, на той же стороне ноды. Это соответствует проверенному подходу JointJS Record и GoJS ScrollingTable.
3. Для collapse можно показывать концы у header / свернувшегося раздела. Это **наше предложение**, а не установленное общее поведение конкурентов; требуется выбор пользователя.
4. Несколько исходных портов могут иметь одинаковую видимую позицию, сохраняя отдельные ID и рёбра. Счётчик и объединение линий — отдельная UX-задача; они не обязательны для проверки корректности геометрии.
5. Общая точка скрытых полей сначала служит индикатором существующих связей. Создание новой связи требует выбора конкретного поля, поэтому не стоит молча выбирать его по общей точке. Приложение может раскрыть/прокрутить список для выбора.

Минимальная альтернатива: demo управляет видимостью рёбер к скрытым строкам, сохраняя сами записи и их endpoints. Она проще визуально, но скрывает часть зависимостей; в исследованных источниках это не найдено как обязательная политика React Flow.

Границу реализации следует выбрать после прогона демо: core обеспечивает достоверное обновление геометрии и стабильную привязку, композиция UI определяет представление скрытого endpoint. Универсальный registry, plugin API и виртуализация строк из этого исследования не следуют.

Проверки для демо: scroll вверх/вниз при разных zoom; collapse/expand; rename/reorder; resize ноды; сохранение ID и количества связей; корректное восстановление позиции; обе стороны ноды; несколько связей с совпадающей proxy-позицией; отсутствие подключения к случайному скрытому полю. Виртуализацию с удалением строк из DOM надо проверять отдельно, если она войдёт в scope.

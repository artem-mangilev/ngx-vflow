# Flow design system: план перехода от MVP к production

Статус: реализация начата по запросу пользователя. Этапы 1–5 реализованы в значительной части; полная приёмка этапа 6 и major-миграция этапа 7 ещё не завершены. Точные результаты, ограничения и оставшиеся работы — в [implementation.md](implementation.md). Исходный план: 2026-09-07; checkpoint: 2026-09-10.

Основание: [исследование](research.md), [обзор аналогов](ecosystem-research.md), текущий MVP в `libs/ui` и три примера на странице Design system.

## Согласованные решения

- Задача — стабильные составные части node-based UI: их назначение, анатомия, композиция, состояния и CSS token contract. Конкретное визуальное оформление будет настраиваться в следующих задачах.
- Бизнес-логика и содержимое принадлежат приложению. Основа библиотеки — UI primitives, а не готовая бизнес-модель редактора.
- Общие части поставляются через `@vflow/ui`, специализированные наборы — через secondary entry points, начиная с `@vflow/ui/bpmn`. Они используют публичные примитивы и токены основы. Отдельный пакет оправдан самостоятельным выпуском или существенными дополнительными зависимостями; пустые пакеты и registry/plugin API не требуются.
- Проверить шесть архетипов: карточка, сущность со строками, событие, развилка, контейнер, связь. Пять reference compositions размещаются на отдельных страницах новой ng-doc секции Design system: workflow, data/media pipeline, ERD/schema mapping, relationships/metrics map и BPMN. Покрытие принято в Q18 по [исследованию потребителей](consumer-patterns-research.md).
- Поставлять `@vflow/ui/styles.css` (готовый CSS по умолчанию) и `@vflow/ui/styles.source.css` (исходный CSS для pipeline потребителя). Оба выхода получаются из одного источника при одной Angular-сборке. Tailwind не обязателен для готового CSS; source-вход не обещает автоматического удаления неиспользуемых правил. Основание — [исследование поставки](tailwind-delivery-research.md).
- Начальный BPMN subset: task, start/end event, XOR/parallel gateway, pool/lane, sequence/message/association links. Дополнительные символы событий, разновидности tasks, subprocess markers и boundary attachment не включены в согласованный базовый список.
- После проверки новых блоков удалить default presentation из core. Core становится headless в отношении готового представления нод и линий: потребитель предоставляет своё UI либо использует `@vflow/ui`. Граница переноса определена в [ADR-0006](../../docs/adr/0006-ui-presentations-core-interaction-feedback.md); техническая миграция прежних типов должна соответствовать этому пути потребления.
- Владение темой определено в [ADR-0005](../../docs/adr/0005-independent-core-theme-contract.md): core имеет свои токены с дефолтами для standalone-потребления, тема UI переопределяет их своими значениями.
- Controls библиотеки ограничены управлением вьюпортом: zoom in, zoom out, fit view и возможность добавить свою кнопку. Переключатель редактирования (замок), form controls и готовые бизнес-действия нод в этот набор не входят; базовое оформление кнопки из MVP рассматривается отдельно от каталога готовых команд.
- Оформление настраивается через CSS: общие значения темы — семантическими токенами, детали частей — обычными CSS-правилами. Каталог component tokens не вводится. Параметры вроде `resizerColor` удаляются при major-миграции. Приоритет общих токенов: пользовательское переопределение → значение из темы UI → дефолт core. Импорт UI CSS сам по себе не должен темизировать standalone flow за пределами явно выбранной области темы.
- Toolbar и minimap используют тему редактора; локальные токены отдельной ноды наследуются только по DOM, без автоматического копирования в другие слои.
- На первом этапе обязательная браузерная приёмка ограничена Chromium. Firefox/WebKit в обязательный набор этого этапа не входят.
- Принята модель независимых состояний: core сообщает взаимодействие и валидность текущего соединения, приложение определяет диагностику, прикладные статусы и допустимые действия. Общая UI-основа предоставляет индикатор с семантическим тоном, произвольной подписью/иконкой и необязательной активностью; диагностика и прикладной статус могут показываться одновременно. Активность сама по себе не блокирует действия. Это не перенос workflow lifecycle в core.
- Стартовый набор общих CSS-токенов Q16 зафиксирован в [рабочем контракте](contract-proposal.md); детализацию токенов пока не расширяем.
- Scroll/collapse полей сначала исследуется в нашем демо. На этом этапе новый публичный контракт или специальное поведение в библиотеку не закладывается; решение о дальнейшем поведении принимается после просмотра демо.
- Контейнер — общая рамка с заголовком вокруг нескольких нод. Правила родительства и совместного перемещения задаются моделью графа; специализированные правила pool/lane относятся к BPMN-набору.

## Scroll/collapse: проверка текущего кода

Это результаты чтения кода, не browser-проверка поддержки сценария. `node-handles-controller.directive.ts` обновляет измерения после render и resize, но не подписывается на scroll. При удалении handle из DOM связь с этим handle ID становится detached; скрытие через `display:none` может сохранить последнюю измеренную геометрию. Поэтому наличие измеряемых row anchors не подтверждает корректный scroll/collapse.

Демо исследует scroll при нескольких zoom, совпадение endpoints с видимыми строками, сохранение field/handle IDs и graph edges при collapse/expand, восстановление геометрии после expand и конфликты scroll с жестами графа. Можно пробовать способы отображения скрытых endpoints локально в демо. Найденные ограничения и дефекты фиксируются как результат эксперимента; это не основание заранее добавлять библиотечный API или объявлять универсальную поддержку scroll/collapse.

По запросу пользователя выполнено [исследование скрытых endpoints](hidden-endpoints-research.md) по документации и исходникам React Flow, JointJS и GoJS. Перенос к границе при scroll и к заголовку при collapse остаётся вариантом для демо, а не принятой библиотечной политикой.

## Viewport controls: проверка ориентира

React Flow Controls содержит zoom in, zoom out, fit view и переключатель interactivity. В исходнике последний меняет `nodesDraggable`, `nodesConnectable`, `elementsSelectable`; он не переключает pan/zoom камеры. Пользователь выбрал для нашего набора только три действия вьюпорта, без замка. Источники: [Controls API](https://reactflow.dev/api-reference/components/controls), [Controls.tsx](https://github.com/xyflow/xyflow/blob/main/packages/react/src/additional-components/Controls/Controls.tsx), проверено 2026-09-07.

В ngx-vflow уже есть публичные `zoomTo`, `fitView` и сигнал `viewport` у `VflowComponent`. Реализацию controls следует строить на публичном API core; текущие UI primitives не импортируют core, поэтому зависимость flow-aware controls нужно явно отразить в package metadata и выбрать место интеграции.

## CSS-миграция: найденные точки программного оформления

Исходный перечень для миграции, не исчерпывающий аудит. Имена CSS-замен ещё не выбраны.

| Текущее API                           | Место                                        |
| ------------------------------------- | -------------------------------------------- |
| `resizerColor`                        | `ResizableComponent`                         |
| `maskColor`, `strokeColor`            | `MinimapComponent`                           |
| `lineColor`                           | `AlignmentHelperSettings` / alignment helper |
| `color`                               | `SelectionBoxSettings`                       |
| `color`, `backgroundColor`            | Варианты `Background`                        |
| `color`, параметры оформления маркера | `Marker`                                     |
| `style` стандартной подписи           | `DefaultEdgeLabel`                           |

При планировании замены разделить оформление и данные/поведение: цвет направляющей и её допуск прилипания имеют разные обязанности. Для canvas minimap потребуется чтение разрешённых общих CSS-значений темы и обновление при изменении поддерживаемой темы; простая подстановка строки `var(...)` в canvas не завершает миграцию. Каждый удаляемый input не обязан получать персональный токен: используются общая палитра и обычный CSS там, где есть DOM/SVG-часть. Точный механизм обновления canvas ещё выбирается.

## План реализации

### 1. Зафиксировать исходную точку и организовать ng-doc

Создать категорию `apps/docs/src/app/categories/design-system/ng-doc.category.ts`. Перенести текущую страницу из Introduction в обзор новой секции, а существующие workflow, entities и BPMN demos — на отдельные страницы. Добавить страницы data/media pipeline и relationships/metrics map по мере появления работающих примеров. Сохранить полезную документацию MVP и обновить ссылки на прежний маршрут.

Запустить существующие проверки MVP и снять исходные измерения выбранной rich-node сцены до изменения примитивов. Использовать текущие Playwright и benchmark-инструменты проекта. Обзор секции объясняет границу core/UI, подключение и CSS-контракт; каждая из пяти страниц показывает отдельную композицию, её код и ограничения.

Готово, когда существующие demos работают после переноса, ссылки корректны и сохранён воспроизводимый baseline. Пустая страница не считается реализацией сцены.

### 2. Стабилизировать общую анатомию и состояния

Доработать существующие primitives в `libs/ui`, экспортируя минимальный набор для согласованного каталога. Использовать обычные HTML-элементы, CSS и content projection; отдельная директива нужна только там, где даёт устойчивую семантическую часть или поведение. Зафиксировать публичные селекторы частей и способы композиции. Прикладные формы, картинки, графики, заметки и меню остаются пользовательским содержимым.

Развести состояние взаимодействия, диагностику, прикладной статус и доступность действия. Предоставить общий индикатор с тоном, содержимым и необязательной активностью. Если композиции требуют отсутствующего публичного состояния core, добавить только конкретный необходимый публичный hook; не обращаться к `ɵ` API. Сохранить владение wrapper semantics и focus в core.

Готово, когда карточки, строки, порты, контейнер и toolbar собираются без копирования реализации оболочек, а статус, диагностика и выделение могут отображаться одновременно. Интерактивное содержимое имеет корректные accessible names и не конфликтует с жестами графа.

### 3. Внедрить CSS-контракт и оба способа поставки

Применить зафиксированные общие токены из [контракта](contract-proposal.md). Core определяет свои fallback-значения; явно выбранная область UI-темы связывает их с `--vui-*`. Детали частей оформляются обычным CSS через публичные селекторы. Проверить наследование HTML/SVG, общие markers, toolbar и canvas minimap. Для minimap реализовать и документировать конкретный способ обновления разрешённых CSS-цветов при поддерживаемом переключении темы.

Выделить единый исходник собственных стилей из текущего `libs/ui/src/styles.css`, отделив локальные директивы генератора. Из него получать `styles.css` и публиковать `styles.source.css`; добавить assets/exports/sideEffects в существующую сборку и package metadata. Source-потребитель не должен зависеть от путей монорепозитория или отсутствующих исходных файлов. Документировать подключение одного из двух входов и реально необходимые инструменты source-pipeline. Сохранить одну реализацию стилей; второй Angular build и отдельный пакет не нужны.

На этом этапе составить полный список appearance inputs и их замен; окончательное удаление выполнять в этапе 7. При временном сохранении старых inputs явно отделить совместимость от нового CSS-контракта.

Готово, когда две разные темы и core-only flow сосуществуют, все заявленные слои обновляются, оба CSS-входа работают из собранного пакета и дают одинаковый результат в одинаковой теме. Импорт CSS не включает тему глобально. Чистая смена цвета не пересчитывает геометрию графа.

### 4. Завершить связи, viewport controls и BPMN entry point

Довести UI связей: видимая линия, маркеры, подписи у начала/середины/конца и пользовательские действия. Маршрутизация, hit targets и геометрия остаются у core. Обеспечить контейнер с заголовком и возможность его собственных соединений без нового механизма родительства.

Добавить zoom in, zoom out, fit view и место для пользовательской кнопки. Использовать публичные `viewport`, `zoomTo`, `fitView` core и его ограничения масштаба. Предлагаемый минимальный способ интеграции — передаваемая ссылка на экземпляр flow; если существующий публичный контекст уже решает задачу, использовать его. Реальную зависимость от core отразить в package metadata; не создавать сервис-регистратор редакторов.

Перенести специализированные BPMN primitives в `@vflow/ui/bpmn`, убрать их из общего агрегата, завершить согласованный subset. Проверить подписи, anchors и представления sequence/message/association. Семантика исполнения и валидация BPMN-модели принадлежат приложению.

Готово, когда controls работают с нужным экземпляром flow и ограничениями zoom, связи и подписи корректны при изменении геометрии, а BPMN импортируется через отдельный entry point и не требуется общим потребителям UI.

### 5. Довести пять эталонных композиций

| Страница новой секции     | Что она должна доказать                                                                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workflow                  | Карточки, ветвление, несколько выходов, подписи связей, пользовательские действия, независимые статус и диагностика                               |
| Data/media pipeline       | Типизированные подписанные порты, богатое содержимое body, пользовательские controls внутри ноды, корректная связь с геометрией портов            |
| ERD/schema mapping        | Строки с портами, стабильные field/handle IDs при rename/reorder, явная прикладная обработка удаления поля; отдельный scroll/collapse эксперимент |
| Relationships/metrics map | Контейнер с собственными connections, заметка без портов, пользовательские метрики/изображения, режим просмотра                                   |
| BPMN                      | Task, start/end, XOR/parallel, pool/lane, sequence/message/association; внешние подписи и согласованная тема                                      |

Использовать общие библиотечные части и локальные данные/обработчики приложений. Не добавлять движки форм, графиков, Markdown или исполнения процессов ради демонстрации содержимого. Scroll/collapse исследовать локально и записать результаты: сохранение модели, отображение скрытых endpoints, восстановление при expand, zoom и конфликты жестов. Возможные ограничения демонстрационного подхода обозначить явно; библиотечный API из эксперимента автоматически не следует.

Готово, когда каждая сцена работает на отдельной странице и покрывает свою строку матрицы. Количество карточек или страниц не заменяет проверку паттернов.

### 6. Проверить новые блоки до удаления defaults

Применить [матрицу приёмки](contract-proposal.md): композиция, геометрия, состояния, доступность, темы, поставка и производительность. Расширять существующие тесты на реальные риски, не заводить тест для каждого пассивного CSS-селектора. Обязательный браузер — Chromium.

Проверить три способа потребления собранных артефактов: core с собственными шаблонами без UI; UI с compiled CSS без Tailwind; UI с source CSS через поддерживаемый pipeline. Отдельно проверить импорт BPMN. Использовать существующие режимы docs/consumer-сборки, дополняя их минимальным consumer только для непокрытых условий. Проверить заявленную Angular-совместимость выпуска.

Готово, когда новые блоки прошли матрицу и есть воспроизводимые результаты. Это обязательный рубеж перед удалением готовых представлений core.

### 7. Выполнить major-миграцию core и финальную приёмку

После этапа 6 удалить default node/group/edge/label presentation и программные appearance inputs. Согласованно обновить публичные типы, create helpers, NodeModel, default handles/оптимизированные пути, minimap, примеры и документацию. Не оставлять тип, который принимается TypeScript, но больше ничего не рисует. Сохранить минимальную обратную связь core по [ADR-0006](../../docs/adr/0006-ui-presentations-core-interaction-feedback.md).

Написать migration guide с двумя рабочими путями: собственные шаблоны поверх headless core и представления из `@vflow/ui`. Для каждого удалённого styling input показать общие токены или публичный CSS-селектор; координаты, constraints и другие параметры поведения сохранить. Обновить README и документацию секции. Версии и публикация следуют существующему release-процессу репозитория; вручную создавать независимый цикл релизов UI не требуется.

Повторить затронутые проверки этапа 6 на итоговом API и собранных пакетах. Готово, когда оба пути миграции компилируются и работают, defaults больше не входят в core, а геометрия, доступность и взаимодействия проходят финальную приёмку.

## Зависимости и завершение проектирования

Базовый порядок: 1 → 2 → 3 → 4 → 5 → 6 → 7. Демонстрации развиваются вместе с соответствующими примитивами; этап 5 завершает их покрытие. Удаление defaults зависит от успешного этапа 6, итоговый выпуск — от повторной проверки после этапа 7.

Пользовательские решения о составе, состояниях, токенах, документации и CSS-поставке зафиксированы. Осталось заключительно согласовать этот план и предложенную [матрицу production-приёмки](contract-proposal.md). Численный performance-бюджет следует установить после baseline-замера; приведённый там размер сцены пока является предложением для проверки, а не обещанием ёмкости. Точные Angular signatures и механизм обновления minimap выбираются при реализации по результатам интеграционных проверок в заданных границах, без расширения продуктового scope.
